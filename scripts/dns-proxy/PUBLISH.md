# Как опубликовать патч и проверить установку с GitHub

## 1. Подготовить репозиторий

Распакуйте dns-proxy.zip на своём компьютере. Создайте на GitHub новый публичный репозиторий, например `dns-proxy`. Выберите свой аккаунт или организацию. Не включайте GitHub Pages: это не требуется.

Через Add file → Upload files загрузите **содержимое** каталога dns-proxy в корень репозитория:

- install.sh
- dns_proxy.py
- config.json
- providers.json
- SHA256SUMS
- test_memory.py
- README.md
- PUBLISH.md
- .gitattributes
- .gitignore

Не загружайте папку верхнего уровня как вложенную: install.sh должен открываться непосредственно по адресу `https://github.com/OWNER/REPO/blob/main/install.sh` (если основная ветка main).

Не публикуйте рабочую папку work, БД панели, state/undo файлы, журналы, SSH-конфигурацию, UUID, ключи или сертификаты. В подготовленном ZIP этих серверных данных нет. DNS-адреса публичных провайдеров в providers.json предназначены для публикации.

## 2. Создать закреплённый релиз

На странице репозитория откройте Releases → Create a new release. Создайте новый тег **v0.2.2** на коммите с загруженными файлами. Назовите релиз `dns-proxy v0.2.2` и опубликуйте его.

Проверьте в браузере:

```text
https://raw.githubusercontent.com/OWNER/REPO/v0.2.2/install.sh
https://raw.githubusercontent.com/OWNER/REPO/v0.2.2/SHA256SUMS
```

Замените OWNER/REPO реальными значениями. Должен отображаться текст файлов, не 404. Не передвигайте опубликованный тег на другой коммит. Для исправлений выпускайте новую версию.

SHA256SUMS уже подготовлен для файлов этой сборки. Если измените dns_proxy.py, config.json или providers.json, перед загрузкой пересчитайте хеши. Изменение README/PUBLISH/тестов не меняет хеши полезной нагрузки. Пример в локальном PowerShell из каталога патча:

```powershell
$payloadFiles = @('dns_proxy.py', 'config.json', 'providers.json')
$manifestLines = foreach ($payloadFile in $payloadFiles) {
    $content = [IO.File]::ReadAllText((Join-Path $PWD $payloadFile)).Replace("`r`n", "`n")
    [IO.File]::WriteAllText((Join-Path $PWD $payloadFile), $content, [Text.UTF8Encoding]::new($false))
    $digest = (Get-FileHash -Algorithm SHA256 -LiteralPath $payloadFile).Hash.ToLowerInvariant()
    "$digest  $payloadFile"
}
[IO.File]::WriteAllText((Join-Path $PWD 'SHA256SUMS'), ($manifestLines -join "`n") + "`n", [Text.UTF8Encoding]::new($false))
```

Менять install.sh также нужно только в новом проверенном релизе: начальный Bash-скрипт ещё не защищён последующей проверкой полезной нагрузки.

## 3. Передать ссылку для совместной проверки

Пришлите в чат URL опубликованного репозитория и тег v0.2.2. Я проверю доступность файлов и соответствие хешей до запуска на сервере.

На втором сервере в этой задаче выполнялись только аудит и dry-run. Патч там не применялся, исходные DNS и sniffing сохранились. Поэтому предварительно откатывать его сейчас не нужно. Не выполняйте откат по чужой или отсутствующей записи.

Применение второго сервера, создание файлов установщика/state и перезапуск ещё требуют отдельного согласования. Для совместного теста область записи будет:

- выбранный путь загрузки install.sh;
- `/var/tmp/dns-proxy-download.*` — временная загрузка;
- `/usr/local/lib/dns-proxy/<HASH>/` — сохранённый код и конфигурация пакета;
- `/etc/x-ui/x-ui.db` — только поля патча;
- `/etc/x-ui/dns-proxy-state/` — точечные записи отката;
- разрешённый перезапуск x-ui и, если выбран возврат, активация отката.

Никаких пакетов, обновлений Xray/GeoSite или чтения приватных ключей не требуется. Учтите краткое прерывание соединений при перезапуске; изменение общих DNS/direct может затронуть Hysteria.

## 4. Установить с GitHub в две команды

Команды выполняются на целевом Linux-сервере в SSH-терминале:

```bash
curl -fL https://raw.githubusercontent.com/OWNER/REPO/v0.2.2/install.sh -o dns-proxy-install.sh
sudo bash dns-proxy-install.sh --repo OWNER/REPO --ref v0.2.2
```

Если вошли как root, sudo можно убрать. Установщик:

1. Загружает три файла полезной нагрузки и проверяет SHA256SUMS.
2. Сначала спрашивает DNS-Proxy и тип адреса — DoH или основной IPv4.
3. Проверяет совместимость и показывает план/предупреждения.
4. Ожидает подтверждение пользователя. По умолчанию отмена.
5. Создаёт точечный откат, применяет настройки одной транзакцией, перезапускает x-ui и проверяет процесс Xray.
6. Предлагает проверить сайты и выбрать результат.

Запишите показанный путь state-файла и точную команду отката. Не закрывайте терминал до последнего меню. Для совместной проверки можно оставить меню открытым, проверить сайты через клиент и затем выбрать нужный результат.

## 5. Проверить повторное применение и откат

После первого успешного применения проверяем:

- Gemini и обычные сайты на нужных inbound;
- verify с тем же DNS-адресом;
- повторную установку с тем же адресом: нет изменений БД, дублей и перезапуска;
- при согласованном возврате — rollback и возвращение исходных DNS/direct/sniffing.

Команда возврата печатается установщиком. Её общий вид:

```bash
sudo python3 /usr/local/lib/dns-proxy/HASH/dns_proxy.py rollback --restart --state /etc/x-ui/dns-proxy-state/FILE.json
```

Не подставляйте буквальные HASH/FILE — используйте реальные пути из вывода. При необходимости повторной установки после отката снова запускайте Bash-команду той же версии. State-файлы не перезаписываются.

Пока это инструкция будущего теста: фактическая установка с вашего GitHub не выполнялась, поскольку репозиторий ещё не опубликован и разрешение на изменение второго сервера ещё не дано.
